# RAP / RAP-SLAM → AutoDL 迁移评估

日期：2026-10-24（Asia/Shanghai）。范围：只读盘点、平台文档核对与未来迁移方案；未租用实例、连接云端、上传文件、启动 WSL、安装软件或执行模型/求解器。目录元数据观测时间：2026-10-24T02:04:14.1058562Z。

## 结论与建议配置

可以迁移，核心离线计算链已有 Linux/WSL 基础，迁移路线清楚。建议采用“独立冷备份 + 云端按实际版本恢复环境 + 分层验收”，不要把整块 WSL VHD 当作可直接启动的 AutoDL 镜像，也不要只 git clone 上游仓库。

首迁优先 **1 × RTX 5090 32GB、至少 16 vCPU、64GB RAM、500GB 本地工作数据盘**；300GB 可作为不保存多份大归档的紧凑方案。CPU/内存通常随主机的单卡配额分配，购买时筛选满足要求的主机，不能假定任意一张 5090 都附带上述资源。先按量租用，不先包月。

| 方案 | 配置目标 | 适用及限制 |
| --- | --- | --- |
| 首迁优先 | 5090 32GB / 16 vCPU / 64GB RAM / 500GB 工作盘 | 本机 5070 与 5090 的 NVIDIA 计算能力同为 12.0；更贴近现有 CUDA 12.8 与编译目标，有助于减少架构切换变量，仍须验收 |
| 节省计算费用 | 4090 24GB / 12–16 vCPU / 48–64GB RAM / 300–500GB 工作盘 | 合理的后续方案；本地 build_p3d.sh 明确只指定 12.0，换 4090 需要核验并可能按目标架构重编译扩展，不能直接承诺二进制可用 |
| 较大多视图/点数 | 单卡 48GB 档 / 16–32 vCPU / 96–128GB RAM | 只有实测 24/32GB 显存不足时再考虑；尚无该工作负载的完整显存峰值证明 |
| 多卡/A100/H800 | 暂不作为首次选择 | 已检查 backend 使用单个 cuda 设备；多买 GPU 不会自动使当前调用链并行，也不能替代 CPU/IO 与算法排查 |

上述是容量规划估计，不是经云端完整 RAP/SLAM 压测得出的最低配置。旧 RI1 的 9216MiB 空闲显存门槛是该次预检阈值，不等于完整工作负载的显存需求；本机约 12GB 显存也不是“所有流程已完整通过”的证据。CPU 原生 KISS/ICP、地图与 IO 同样影响端到端速度，不能仅按 GPU 算力比推算加速。

优先普通容器实例的本地 SSD/NVMe 工作盘，适合逐帧点云读取。普通实例系统盘默认30GB且不支持扩容；不要把全部 Conda、编译缓存和数据塞在系统盘。将较大环境/缓存放在工作数据盘并单独备份，系统镜像不会包含这些挂载数据。如果选 Pro，需要改为扩容其系统盘；Pro 无独立数据盘，其网络系统盘性能和价格机制也不同，不能把两种产品的配置直接套用。[AutoDL 环境和磁盘](https://backup.autodl.com/docs/env/)、[普通实例与 Pro 对比](https://www.autodl.com/docs/instance_pro/)。

## 环境恢复路线

10月22日实际环境记录、10月23日复核记录与原始安装脚本有明显差别。下面是已有记录，不是本次新启动 WSL 后的实时环境导出：

| 入口/用途 | 已记录关键版本 |
| --- | --- |
| RAP Conda /root/miniconda3/envs/rap-inference | Python3.10.20、torch2.7.0+cu128、pytorch3d0.7.9、NumPy1.26.4、Open3D0.19.0、GTSAM4.2、KISS-ICP1.3.0 |
| 原生 SLAM venv /root/venvs/kiss-slam-hc1 | Python3.12.3、NumPy2.2.6、Open3D0.20.0、KISS-SLAM0.0.2、KISS-ICP1.3.0，map_closures 原生模块曾导入通过 |
| /usr/bin/python3 | 系统 Python3.12.3 与相关系统依赖 |
| Miniconda base | Python3.14.6，用作环境管理入口 |

这是四个解释器入口，并非四个独立 Conda 环境。不要将两套不同 NumPy/Open3D 的运行角色合并成一个“全装进去”的环境。ros2/run_step1.sh 还依赖 /opt/ros/jazzy 和 RViz/WSLg。

主路线：先归档 WSL 与项目，再以实际环境锁、源码和编译材料在云端恢复。RAP Conda 可尝试用 conda-pack 保留当前环境，再在兼容的 Linux x86_64/系统库条件下解包和修复前缀；它不能包办驱动、系统库、CUDA架构、ROS、可编辑安装或外部源码路径问题。原生 venv 不应只复制目录，需保存其 Python 基础、完整依赖版本、源码/原生模块以及系统库清单，必要时重建。[conda-pack 官方说明](https://conda.github.io/conda-pack/)。

优先核对能否选与本机 Ubuntu24.04 相近的用户空间；早期环境记录为 glibc2.39，放到较老 Ubuntu 镜像时尤其要检查 GLIBC/GLIBCXX/ABI。AutoDL网页的框架默认Python不一定是3.10，应显式恢复项目解释器。不要直接执行 scripts/install.sh：它固定 torch2.5.1/cu124，与本机实际路线不同；也不要用 build_p3d.sh 的未固定上游最新源码重建来代替保存本机准确构建版本。

现有 build_p3d.sh 的 TORCH_CUDA_ARCH_LIST=12.0 是首迁偏向5090的依据之一，并不证明已安装所有 .so 都只含该目标。NVIDIA列5070/5090为CC12.0：[GPU架构表](https://developer.nvidia.com/cuda/gpus)。驱动由云平台宿主机提供，先核验其兼容性，不把本机 Windows 驱动复制到容器。

AutoDL普通实例本身是容器，官方说明容器内不支持再使用Docker；不能默认在其内部 docker load 本机镜像即可完成迁移。先用平台基础镜像恢复用户空间，成功后保存平台镜像。[平台说明](https://backup.autodl.com/docs/env/)。

## 执行顺序与交付物

1. **冻结源端并制作完整清单。** 记录两个仓库的HEAD、分支、dirty状态、未跟踪/被忽略的重要文件；列出数据、模型、代码、论文/图表、配置、环境、编译源码/补丁及外部路径。输出相对路径/长度/SHA256清单、链接清单和路径映射。执行时补充 WSL 内 /root、/home、/opt 下项目相关材料盘点。本次没有做全盘或WSL内部逐文件盘点。
2. **先做独立冷备份。** 新导出的当前WSL备份，加上 Windows项目、数据、记录，复制到不随这台电脑退役的介质或独立对象存储，建议1TB外置SSD。验收归档内容与SHA256，尝试恢复读取；旧VHD备份和兼容Junction保持原状，不通过旧链接删除内容。
3. **锁定两套运行环境。** 保存实际 pip/conda/apt版本、编译器、CUDA toolkit、原生库ldd信息、构建源码提交与补丁、wheel及可编辑路径。配置导出和本地原始恢复包分开保存；凭据单独处理，上传包不夹带个人SSH私钥/API token。不修改已封存的源/证据文件。
4. **按量创建一台目标主机。** 优先5090单卡、16vCPU/64GB、普通实例500GB工作盘，核对地区文件存储、主机租用截止、平台镜像用户空间、驱动和网络。先上传少量环境材料/合成检查，再决定是否长租。
5. **分批传输并核对。** 先环境、代码、权重及少量公开输入，后数据和历史档案。用SSH/SFTP或rsync断点续传；众多小文件按目录分成可校验归档，保留Linux链接/权限，避免一个难以续传的超大包。两端逐文件或按归档及内层清单SHA256比较。官方支持SCP/SFTP等：[上传文档](https://www.autodl.com/docs/scp/)。
6. **恢复路径和环境。** 云端实际数据可放 /root/autodl-tmp/githouse；初期通过可审计的兼容路径暴露 /mnt/e/githouse，避免批量改动历史脚本和哈希。C盘工作/记录路径也需要映射。长期再另行参数化路径。环境移位需修复前缀与可编辑安装；旧绝对路径不能仅靠改一个配置解决。
7. **分层验收。** 文件/归档完整性 → 两套解释器和原生库导入 → GPU合成算子/自定义扩展 → 非模型的公开输入与路径接口 → 在单独定义的迁移验收范围内做最小真实模型功能检查及短序列。逐级保存命令、配置、数据/权重哈希、日志、RAM/显存峰值与返回码；不直接跑全套历史研究。
8. **验证独立使用与恢复。** 从另一台电脑经SSH连接，确认旧电脑离线后仍能读取数据和运行已验收入口；做关机再开机、路径恢复、备份恢复测试。保存系统镜像并单独保存数据盘/环境包，之后再退役旧电脑。建议保留旧盘或冷备份至少2–4周。

迁移验收不自动重开已关闭的RI1/CB1/TT1或其他试验，不安装历史候选修复，不覆盖旧失败、预算或科学结论；新增迁移记录单独保存。先把既有状态完整带过去，再单独解决运行问题。

## 风险与处理

| 风险 | 本项目依据 | 处理与验收 |
| --- | --- | --- |
| 代码之外的材料遗漏 | 多目录、忽略文件、未提交文件、WSL系统库、C盘记录、外部链接 | 清单先行；原始冷备份与云端工作副本独立；全清单验收 |
| CUDA/原生ABI不兼容 | PyTorch3D、PyG等扩展；sm12.0构建脚本；glibc2.39记录 | 首选同代GPU及相近用户空间；保存准确源码/二进制；逐算子验证，必要时重编译 |
| 版本漂移/已知加载关口 | 默认weights-only读取曾拒绝OmegaConf ListConfig；另一tensor候选在stride门槛停止 | 锁版本；不得把迁移当作绕过加载限制的理由；修复另立范围 |
| 数值与速度变化 | 本地同输入ICP已有微小变化，原因未知；P0失败仍在 | 先定义可用性和数值容差，再比对；固定线程/精度/种子仅降低变量，不承诺逐位一致或论文指标改善 |
| 路径/链接/权限 | 大量 /mnt/e、/mnt/c、/root 路径；Linux链接与Windows Junction | 显式映射、保留Linux语义、检查外部依赖，原证据保留原路径文本 |
| 云端单副本丢失 | 本地数据盘无冗余；普通/Pro均有释放规则 | 同地区文件存储保存重要资料，另有平台外备份；保留到期提醒与恢复说明 |
| 显存/内存仍不足 | 尚无完整目标工作负载云端峰值 | 起步64GB RAM/32GB显存；先小样本测量后决定48GB或更大档，不自动扩大历史实验上限 |
| GUI与ROS/硬件接口 | RViz脚本明确依赖WSLg；可能有ROS2/设备输入 | 首迁验收离线计算；图形通过远程桌面/导出，机器人实时连接另评网络与设备接入 |
| 操作端中断/空闲费用 | SSH断开、CPU阶段GPU低使用率、云盘持续付费 | tmux/进程托管与日志；检查平台空闲关机设置；结束后主动关机；不在本评估中建立自动任务 |

AutoDL普通实例连续关机15天可能释放；Pro为60天。保存镜像主要保存系统盘，普通实例工作数据盘不在镜像内。文件存储可供同地区实例共享且不受单实例释放影响，但IO较弱，适合作为重要资料存储；活跃点云复制到本地工作盘使用。所有平台存储仍需平台外第二份备份。[数据保留](https://backup.autodl.com/docs/instance_data/)、[Pro数据](https://www.autodl.com/docs/instance_pro_data/)、[保存镜像](https://backup.autodl.com/docs/save_image/)、[文件存储](https://www.autodl.com/docs/fs/)。

## 把握、工期与费用

以下是基于现有材料的主观工程信心，非实测成功率或统计保证：

- **完整保存已识别代码、数据与证据：高，约95%以上。** 前提是新冷备份、两端完整校验和独立恢复检查全部通过；当前只是元数据盘点，尚未满足此验收条件。
- **恢复两套核心离线运行环境：较高，约80%–90%。** 已有Linux基础和具体版本记录，有可能需要处理编译/系统库/路径；云端尚未测试。
- **所有研究分支、真实RAP加载与完整序列一次全部通过：目前不宜给高承诺。** 已有关闭的加载/资源关口，迁移本身不解决它们。
- **历史结果逐位相同、原研究结论转为成功：不承诺。** 研究仍UNRESOLVED、稿件仍PAUSED；硬件迁移与科学目标分开验收。

建议留1–3个工作日完成核心离线环境迁移和验收，若原生依赖重编译或ROS图形需要适配，按3–5个工作日预留。上传耗时另受上行带宽限制：125–170GB在20Mbps理论约14–19小时，在100Mbps理论约2.8–3.8小时，实际还需协议/校验/断点重试开销。本次未测速，工期不能视为保证。

## 现阶段未解决的前提

尚无AutoDL账号/实例实际检查、目标地区库存/配额/磁盘最终报价、源端上行测速、WSL内部最新完整依赖导出、完整云端模型验收及全部外部资产覆盖证明。本评估未读取凭据、未解码点云/权重、未进行科学重跑。下一步应先制作最新可恢复冷备份和迁移清单，再按量进行云端小规模环境验收。
